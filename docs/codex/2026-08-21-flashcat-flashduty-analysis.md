# 快猫星云（Flashcat Cloud / Flashduty On-call）调研报告

> 调研日期：2026-08-21（Asia/Shanghai）
> 现场入口：[Flashcat 控制台](https://console.flashcat.cloud/channel)
> 说明：控制台当前产品界面使用 **Flashduty** 品牌；本文将“快猫星云”理解为 Flashcat Cloud 生态，将控制台中的值班/故障产品称为 Flashduty On-call。报告把证据分为“现场观察”“官方文档”“开源证据”“推断”，不把推断写成内部实现事实。

## 1. 一句话结论

Flashduty 是一个把多来源监控事件集中接入、降噪、分派、通知和协作处置的 SaaS On-call 平台。它的核心不是监控规则计算，而是把 **Event → Alert → Incident（故障）** 做成可配置的响应流水线：先在事件层去重/聚合，再在告警层聚合成故障，然后按协作空间、路由和分派策略通知值班人员，最后以认领、关闭、时间线、状态页和复盘完成闭环。

它的产品设计重点有三个：

1. 用“协作空间”作为租户内的责任边界和配置容器；
2. 用“事件聚合、告警聚合、抖动、静默、抑制”分层解决噪声，而不是只提供一个模糊的去重开关；
3. 把连接器、路由、值班、升级、通知模板、表单和 API 放入统一控制面，并用订阅版本和权限控制功能暴露。

公开代码主要是 API/自动化入口（Go SDK、CLI、MCP Server、采集器和 Nightingale 部署组件），没有公开 Flashduty 核心服务端代码。因此下面关于后端分片、队列和存储的描述，只有标明“推断”时才表示架构推测。

## 3. 产品定位和信息架构

### 3.1 控制台的导航骨架（现场观察）

左侧主导航按“运行—协作—配置—扩展”组织，现场看到的模块包括：

| 导航区域 | 现场模块 | 产品含义 |
|---|---|---|
| 协作与运行 | 协作空间、故障列表、状态页面、故障复盘 | 以空间承载责任，以故障承载响应，以状态页/复盘承载外部沟通和学习 |
| 数据与分析 | 分析看板、用量数据、分析数据 | 从通知量、故障量、变更量到 MTTA/MTTR 等运营指标 |
| 接入 | 集成中心、告警/变更/即时消息/Webhook/其它 | 把上游监控和下游通信统一纳管 |
| 策略 | 值班管理、服务日历、通知模板、映射数据、过滤条件 | 把“谁接、何时接、接收什么、如何渲染”拆成可复用配置 |
| 数据采集辅助 | 自定义表单、自定义字段 | 在创建、认领、关闭故障时补充治理字段 |
| AI | AI SRE（新对话、自动化、产物、插件、知识库、环境） | 以故障上下文为入口的诊断/自动化扩展 |

这种布局说明 Flashduty 的第一主任务是“把故障交给正确的人”，而不是建立监控规则或维护资源拓扑。控制台把降噪、路由和值班都放在协作空间下，降低了不同团队之间配置互相污染的风险。

### 3.2 协作空间是责任边界

现场的 `Default` 协作空间详情有两个主标签：故障、配置。配置又分为：

- 集成数据、专属集成、排除规则；
- 降噪处理：事件聚合、告警聚合、抖动检测、静默策略、抑制策略；
- 通知分派：分派策略；
- 设置：基础信息、高级配置。

这不是单纯的“项目文件夹”，而是一个完整的响应域：事件在哪里落地、哪些告警被丢弃、如何合并、谁被通知、何时自动关闭，都在同一个边界里决定。共享集成则在账户级接收，再通过路由把事件送到空间；专属集成直接绑定到空间。

## 4. 核心对象模型与生命周期

官方文档明确采用如下关系：

```text
监控系统
   │
   ▼
Event（每次触发/恢复的原始事件）
   │  相同 alert_key 在事件聚合窗口内合并
   ▼
Alert（告警，可包含多个 Event）
   │  相似告警按规则或智能模型聚合
   ▼
Incident / 故障（主要人工处理对象）
   │
   ├─ 分派、通知、认领、升级
   ├─ 时间线、行动项、状态页
   └─ 手动关闭或关联告警全部恢复
```

### 4.1 严重度、处理进度、来源状态是不同维度

- 严重度统一为 `Info / Warning / Critical`；事件按集成映射，告警取其事件最高级，故障取其告警最高级。
- 处理进度为 `Triggered（待处理）→ Processing（处理中）→ Closed（已关闭）`。任何人认领即进入处理中；所有处理人取消认领后可回到待处理。
- 来源状态由关联告警决定：仍有未恢复告警则故障未恢复，全部恢复则故障自动恢复。
- 手动关闭只改变处理进度，并会关闭关联告警，使其不再合入后续事件；自动恢复则来自上游恢复事实。

这套“响应状态”和“监控恢复状态”分离的设计，避免了“有人点了认领”被误解为“根因已恢复”。

### 4.2 标签是跨模块的控制面

标签来自事件 payload，不能在故障上随意手工改写；自动故障默认继承第一条告警的标签，手工故障没有标签。标签被同时用于检索、路由、分派、聚合、静默和抑制。官方还提供标签增强：正则提取、映射表、组合、删除和覆盖规则，并支持预览与规则排序。

## 5. 接入与事件处理流水线

### 5.1 集成模式

官方文档把接入分为：

- **专属集成**：集成直接挂在协作空间，事件天然进入该空间；
- **共享集成**：在集成中心创建一次，通过路由规则按来源、严重度、标签等条件投递到不同空间。共享集成必须至少配置一条路由，否则事件会被丢弃；文档建议增加 catch-all 路由。

现场集成中心列出了大量适配器，包括 Prometheus、Grafana、Zabbix、夜莺/Flashcat、Uptime Kuma、云厂商监控、Sentry、PagerDuty、飞书/钉钉/企微、Slack 等。表格把“集成类型、团队、最近事件、状态、操作”作为一等字段，说明接入健康度也属于控制面，而不是隐藏在日志里。

### 5.2 Prometheus 表单体现的契约

现场打开 Prometheus 集成表单（未保存）可见：集成名、描述、管理团队、Push URL、默认路由协作空间等基础设置；页面同时嵌入 Alertmanager `webhook_configs` 示例，要求 `send_resolved: true`，可选 `proxy_url`。文档/表单对 severity 的兼容映射包括 `critical`、`warning/warn`、`info/acknowledged/unknown/unk`、`ok` 等别名。

Push URL 中含集成凭据，本文不记录实际值。这个页面设计表明 Flashduty 更倾向于“标准化接入契约 + 每个适配器的可复制配置”，而不是让用户自己拼 API 请求。

### 5.3 推断出的处理顺序

结合官方对象模型、控制台配置和降噪文档，可以得到可解释的逻辑顺序：

1. 验证集成并解析事件；
2. 事件聚合（同一 `alert_key` 是否进入既有 Alert）；
3. 标签增强/字段标准化；
4. 共享集成路由到协作空间；
5. 告警聚合形成或更新故障；
6. 静默、抑制、抖动和风暴策略决定是否通知；
7. 分派策略选择人/团队/值班表并安排升级；
8. 写入时间线、统计和后续恢复事实。

这是依据文档和 UI 的行为模型推导的处理图，Flashduty 没有公开核心服务端实现，不能据此断言内部是单体、微服务或某种队列。

## 6. 降噪能力：产品最有辨识度的部分

### 6.1 事件聚合（Event → Alert）

新建协作空间默认开启事件聚合，默认窗口 24 小时，可配置 1–1440 分钟。相同 `alert_key` 在窗口内合入一条告警，超出窗口新建告警；关闭后每个事件都生成独立告警。它解决的是同一监控对象不断重复上报的问题。

### 6.2 告警聚合（Alert → Incident）

新建空间默认关闭告警聚合；开启后多条相似告警只创建/更新一个故障。提供两种模式：

- **规则聚合**：按属性或标签精确匹配；支持统一维度或按条件分支选择维度，分支从上到下命中第一条；
- **智能聚合**：按机器学习语义相似度，默认使用标题、描述、`labels.service`、`labels.resource`，最多选择 10 个字段。

通用配置还包括：

- 固定窗口或“持续合入直到故障关闭”；
- 窗口起点可选故障触发或每次告警合入后重置；
- 风暴预警最多 5 个阈值，每个阈值 2–10,000；
- 严格聚合决定空标签是否视为不同值；
- 规则维度每组最多 5 个、细粒度分支最多 100 条；单故障最多聚合 5000 条告警（文档说明并发下可能略超）。

这比单一的“group by 标签”更接近一个可调的相关性引擎：规则模式提供确定性，智能模式降低首次配置成本。

### 6.3 抖动检测

抖动检测针对同一故障频繁触发/恢复：

- 关闭；
- 仅提醒（标记抖动但继续通知）；
- 提醒后静默（首次提醒后不再通知）。

新空间默认开启“仅提醒”。默认参数是观测窗口 60 分钟、状态变化 4 次、静默 120 分钟，范围分别为 1–1440 分钟、2–100 次、30–1440 分钟。它把“告警真实存在但不值得重复叫醒人”建模为状态，而不是把数据删除。

### 6.4 静默策略

静默用于维护窗口和已知问题，支持：

- 单次时间段；
- 每周周期；
- 依赖服务日历的工作日/休息日周期；
- 按严重度、标题、描述、集成来源、标签组合条件（AND/OR）；
- “直接丢弃”或“保留并标记为静默”。

现场配置页还提供“快速静默”：从故障详情自动带出严重度和筛选后的标签，默认单次 1 天，过期自动删除；系统会排除 JSON、纯数字、时间格式和过长标签，以降低误把瞬时值写进规则的风险。

### 6.5 抑制策略

抑制与静默不同：它要求一个“根因告警”活跃时，自动压制相关次要告警。例如 Critical 存在时抑制同检查项的 Warning/Info。规则同时描述新告警条件、活跃告警条件和两者的相同属性/标签；官方默认回看 10 分钟内、未认领且未恢复的活跃告警。行为同样可选直接丢弃或保留标记。

### 6.6 降噪设计评价

优点是层次清晰：事件去重、告警相关性、状态抖动、计划静默、根因抑制各自有可解释的对象和时间边界。缺点是配置面很大，规则、标签增强、路由和分派之间存在组合爆炸；产品需要预览、命中解释和历史回放，否则高级用户容易“降噪过度”。

## 7. 路由、分派和通知

### 7.1 路由规则

共享集成路由支持精确、通配符、正则等条件，可选择继续匹配或命中即停止，也有默认路由。路由目标缺失时可回退或丢弃。文档还提供规则重排、插入、过滤、历史、差异、恢复和最多 20 条真实告警预览，这说明 Flashduty 把规则变更的可解释性当成产品能力，而不是只提供 JSON 编辑器。

### 7.2 分派策略

协作空间内的分派策略按顺序匹配，第一条成功就停止。每条策略可以设置：

- 生效时间、服务日历和故障过滤条件；
- 0–3600 秒的延迟窗口，故障在窗口内关闭则取消通知；
- 目标为值班表、团队、个人或组合；
- 个人渠道（电话、短信、邮件、App、IM）和群聊机器人；
- 多个升级阶段、重复通知、条件（未关闭/未关闭且未认领）和每阶段等待时间；
- 通知模板以及个人偏好/统一设置。

现场打开默认策略的只读编辑抽屉，看到的字段与上述模型一致：延迟、模板、级联阶段、严重度对应的语音/SMS/邮件、重复提醒和升级条件均以同一个表单组织。它的交互目标是让“何时叫醒谁”可在一次审阅中完成。

### 7.3 通知模板

默认模板为系统预置且不可修改，通道覆盖飞书、钉钉、企微、Slack、Teams、Telegram、Zoom、邮件、短信、语音。正文使用 Go template 风格变量和辅助函数（标签遍历、图片转移、拼接等），支持附加信息和预览数据。模板与分派策略解耦，便于同一策略在不同通道复用。

## 8. 值班、日历和表单

官方值班模型支持：按天/周/自定义周期轮换，白班/夜班，主/备角色，多层规则，临时调班，请假覆盖，日期掩码，连续轮换和公平轮换。交接前通知、每日值班播报可以走个人偏好或统一渠道。服务日历进一步把工作日/休息日抽象成可被静默和分派复用的时间条件。

自定义表单可分别挂在“创建故障、认领故障、关闭故障”三个动作，字段支持必填、条件显示、图片和排序；填写结果持久化在故障或动作记录中。它解决的是响应流程中的结构化上下文，而不是泛化的工单字段。

## 9. 其它产品模块与现场限制

现场观察到：

- 状态页：公开页面配额显示为 `0/1`；内部状态页配额为 `0/0`；
- 故障复盘：提示仅专业版及以上；
- 分析数据：提示标准版及以上；
- 自定义字段、服务日历等部分功能受权限或版本限制；
- 用量看板按通知数、故障/告警/事件数、变更数分组，支持日/周/月和最近两周；
- AI SRE 面板有“新对话、自动化、产物、插件、知识库、环境”，并提示初始化值班链路、告警来源和处置流程；本次没有点击初始化，也没有发送消息。

这些现象反映出 Flashduty 的商业化边界直接呈现在产品 IA 中：基础接入和故障处理可用，高级复盘、分析、AI、服务日历等按版本逐步开放。报告不把禁用按钮解读为产品不存在，只记录本租户当前可见性。

官方产品页在不同区块使用“60+ 告警来源”“50+ 集成”等营销口径，并把 AI SRE、多层聚合/抑制/抖动和套餐作为卖点；这些不等同于本租户已开通的功能。选型时应将“产品页能力、文档约束、租户套餐/权限”作为三个独立核对项，参见 [Flashduty 官方产品页](https://www.flashduty.com/zh)。

## 10. 开源项目与可验证的实现线索

### 10.1 官方组织

[Flashcat GitHub organization](https://github.com/flashcatcloud) 自称“enterprise observability management, ai-powered real-time incident center”，公开组织页列出 60+ 仓库。与 Flashduty 直接相关的项目包括：

| 仓库 | 证据与价值 |
|---|---|
| [flashduty-mcp-server](https://github.com/flashcatcloud/flashduty-mcp-server) | 官方 MCP Server；README 明确采用“小而任务导向”的工具集，而不是把全部 Open API 一比一暴露；支持 stdio 和 Streamable HTTP、toolset、只读模式、日志脱敏；工具覆盖 incident、change、status page、users、channels、fields。 |
| [go-flashduty](https://github.com/flashcatcloud/go-flashduty) | 官方 Go SDK；README 声称由 OpenAPI 生成，覆盖 34 个服务、304 个操作，方法按服务分组，单方法对应一次 HTTP 请求，并可通过 `http.RoundTripper` 组合重试、缓存和 tracing。 |
| [flashduty-cli](https://github.com/flashcatcloud/flashduty-cli) | 官方 CLI；可管理故障、值班、状态页等，支持表格/JSON/TOON 输出和 APP key 配置。 |
| [categraf](https://github.com/flashcatcloud/categraf) | Nightingale 生态的一站式 telemetry collector，基于 Telegraf、Exporters 和 OpenTelemetry，说明 Flashcat 也覆盖上游采集层。 |
| [n9e-helm](https://github.com/flashcatcloud/n9e-helm) | Nightingale Helm chart，提供 K8s 部署、Ingress/ClusterIP/NodePort/LoadBalancer 和持久化配置。 |

### 10.2 从开源代码可以确认什么

可以确认 Flashduty 对外采用 API-first、OpenAPI 生成 SDK、CLI 和 MCP 自动化的路线；MCP 还明确将读写工具分开，并提供只读开关。这与控制台中所有对象都有稳定列表/详情/操作入口相吻合。

不能确认 Flashduty 核心服务端内部采用什么数据库、消息队列、分片策略或机器学习模型；这些部分没有公开源码，任何“必然是 Kafka/微服务/向量库”的说法都属于臆测。

## 11. 产品优势、风险和可借鉴点

### 优势

1. 事件、告警、故障三层模型可解释，降噪策略有明确边界；
2. 共享/专属集成兼顾中心化接入和团队自治；
3. 分派策略、值班表、模板、表单相互组合，覆盖从告警到交接的完整路径；
4. 规则预览、历史、差异、恢复和时间线降低了运营风险；
5. MCP/CLI/SDK 让自动化和 AI 不必依赖浏览器脚本。

### 风险/不足

1. 高级降噪规则多、计划分层多，缺少强解释时容易产生“静默了但没人知道”的风险；
2. 现场页面存在少量文案复用/标题滞后（例如部分子页标题仍显示上一模块），提示 SPA 权限/版本分支较复杂；
3. 核心服务端不可见，企业自托管、数据驻留和故障回放能力需要依赖厂商；
4. 多数高级能力受版本/权限限制，选型时不能只按产品宣传页判断实际可用范围；
5. 告警中心强，但基础设施拓扑、业务影响证据不是其主要对象。

### 对当前项目最值得借鉴的模式

- 事件→告警→故障的可视化层级和“来源状态/响应状态”分离；
- 降噪设置页把默认值、窗口、命中维度、预览和解释放在同一个上下文；
- 共享接入的路由预览/版本/回滚；
- 统一的通知模板与自定义表单；
- 只读 MCP 工具集和 OpenAPI 生成 SDK；
- 把状态页、复盘、用量和 AI 作为故障生命周期的后续环节，而不是另起一套对象。

## 12. 结论

Flashduty 最成熟的部分是“告警响应编排”：它把噪声控制和叫醒策略做成了完整产品。它并不试图取代 Prometheus/Alertmanager 等监控计算系统，也没有把基础设施依赖图和业务影响判断作为第一根对象。对需要快速获得多渠道值班、跨团队路由和低门槛 SaaS 的团队，它是完整的 On-call 方案；对需要解释“哪项共享基础设施导致哪些业务受影响”、并保留证据和人工裁决的团队，还需要补充更强的 Fault/Impact 模型。
